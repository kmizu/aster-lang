# ASTER v0.2.0

ASTER v0.2.0 makes the deterministic runtime usable as a governance boundary
for an external host while keeping ASTER 0.1 source syntax unchanged.

This remains an experimental reference processor. The release does not embed
model, network, filesystem, shell, MCP, or provider SDK authority. Instead, a
host implements only the typed effects it is prepared to execute.

## Host protocol

- `aster host` exposes a strict, versioned, bounded JSON Lines exchange over
  standard input and standard output.
- Every effect follows `effect_preview -> effect_admission -> execute_grant ->
  effect_resolution`. A preview is not authority.
- ASTER reserves variable usage, seals the pending machine continuation, and
  atomically persists its snapshot and trace before emitting a grant.
- Request and execution-grant hashes bind each result to one run, request,
  trace checkpoint, snapshot, and usage reservation.
- `aster host-resume` verifies the durable continuation, repeats the handshake,
  and re-emits the identical outstanding grant without a second admission.
- Protocol input is limited to 1 MiB per line, unknown fields and versions are
  rejected, stdout is protocol-only, and failures use stable redacted
  `ASTER-HOST-11001` through `ASTER-HOST-11006` diagnostics.

The normative contract is in
[`docs/spec/aster-host-protocol-0.2.md`](../spec/aster-host-protocol-0.2.md).

## Self-use evidence

The synthetic `governed-note` example was driven by a coding-agent-style host
through model, read, human approval, write, read-back, and reconciliation. The
temporary file changed only after the matching execution grant. ASTER then
produced a byte-identical final state through driver-free replay with no host
interaction.

This proves the protocol can govern a real host loop; it does not prove a host
is honest. A malicious host can still misuse authority it already possesses,
act before a grant, falsify provider behavior, or under-report usage. Deployers
must use process isolation, least privilege, and provider-specific controls.

## Runtime and compatibility

- Fixture-backed `aster run`, explicit `aster resume`, and `aster replay`
  remain supported through the same pure `RecordSession` implementation.
- Replay has no host or driver parameter and never invokes an external effect.
- ASTER 0.1 source programs remain the language compatibility boundary; the
  host protocol has its own version 1 schema.
- Candidate opacity, write governance, affine permits, budgets, secret
  exclusion, transactional state, trace hashing, and reconciliation invariants
  are unchanged.

## Install

Download the archive for your platform from this release:

- `aster-v0.2.0-x86_64-unknown-linux-musl.tar.gz`
- `aster-v0.2.0-aarch64-apple-darwin.tar.gz`
- `aster-v0.2.0-x86_64-apple-darwin.tar.gz`
- `aster-v0.2.0-x86_64-pc-windows-msvc.zip`

Linux and macOS archives contain `aster`; the Windows archive contains
`aster.exe`. Every archive also contains `README.md` and `LICENSE`.

After extraction:

```bash
./aster --version
```

The expected output is `aster 0.2.0`.

## Verify the download

Download `SHA256SUMS` into the directory containing all four archives, then
run:

```bash
sha256sum --check SHA256SUMS
```

The release binaries are unsigned and the macOS archives are not notarized.
Checksums detect download corruption or substitution but do not establish the
publisher's identity.

## Experimental limitations

ASTER v0.2.0 does not provide arbitrary network or shell execution, embedded
provider integrations, credential storage, trace encryption, packages,
concurrency, loops, recursion, distributed execution, or malicious-host
containment. Traces and snapshots may contain private non-secret data and must
be protected as sensitive artifacts. `Secret<T>` remains forbidden from the
protocol, prompts, logs, diagnostics, traces, snapshots, persistent state,
hashes, and string conversion.
