# ASTER v0.2 Host Protocol Design

**Status:** Approved in conversation on 2026-08-06; written specification
awaiting final review before implementation planning.

## Goal

ASTER v0.2.0 makes the deterministic runtime usable as the governance layer
for a real external host, including a coding agent such as Codex, without
giving the ASTER VM ambient network, process, filesystem, model-provider, or
MCP authority.

The release adds a versioned bidirectional JSON Lines protocol over standard
input and standard output. ASTER remains responsible for capabilities,
budgets, proposals, permits, transactional state, trace evidence, snapshots,
and replay. The host receives only typed effect requests and may execute an
effect only after ASTER has admitted it, reserved its maximum resource usage,
and persisted a continuation.

The source-language version remains ASTER 0.1 because this release adds no
syntax or static semantics. The distribution and runtime version becomes
0.2.0, and the new host protocol starts at schema version 1.

## Non-goals

ASTER v0.2.0 does not embed a model SDK, MCP client or server, HTTP client,
shell runner, arbitrary command executor, native plugin loader, credential
store, or provider-specific adapter. It does not claim to prevent a malicious
host from performing an effect before ASTER sends an execution grant. That
requires process isolation outside the protocol and remains an explicit trust
boundary.

The release does not add packages, concurrency, loops, recursion, distributed
execution, trace encryption, source-level protocol constructs, or a second
write path. Existing fixture execution and driver-free replay remain supported.

## Architectural approach

The implementation will generalize the existing record loop instead of adding
a parallel execution path.

`aster-runtime` will own a pure, transport-independent `RecordSession` state
machine. It steps the VM until it completes, fails, or needs host interaction.
Its public phases are:

1. `AwaitingAdmission`, containing one complete `EffectRequest`.
2. `AwaitingResolution`, containing the admitted request and its
   `ExecutionGrant`.
3. `Completed`, containing the atomic `RunOutcome` and complete evidence.
4. `Failed`, containing the controlled error and all evidence produced before
   failure.

The existing `record_run_evidenced` API will become an adapter over
`RecordSession`: it asks an `EffectDriver` for a preview, admits the declared
maximum usage, asks the driver to resolve the admitted request, and supplies
the result. This preserves the fixture API and gives fixture and host execution
one implementation of admission, tracing, snapshots, settlement, and state
publication.

`aster-runtime` also owns serializable protocol frames and validates their
schema, ordering, request binding, and execution-grant binding. It performs no
stream I/O. `aster-cli` alone maps those frames to line-delimited standard
input and output and writes trace, snapshot, and final-state artifacts.

No dependency direction changes. The path remains:

```text
aster-diagnostics <- aster-syntax <- aster-semantics <- aster-ir
                  <- aster-runtime <- aster-cli
```

## CLI surface

The new start command is:

```text
aster host SOURCE \
  --agent AGENT \
  --event EVENT \
  --input EVENT.json \
  --state STATE.json \
  --capabilities CAPABILITIES.json \
  --trace RUN.trace.jsonl \
  --snapshot-dir SNAPSHOTS \
  --output-state OUTPUT.json
```

The new resume form is:

```text
aster host-resume SOURCE \
  --snapshot SNAPSHOT.json \
  --trace RUN.trace.jsonl \
  --snapshot-dir SNAPSHOTS \
  --output-state OUTPUT.json
```

Both commands reserve standard output exclusively for canonical one-frame-per-
line protocol JSON. Human diagnostics and controlled error summaries go to
standard error. A terminal protocol frame is emitted before a normal or
controlled-error exit whenever the output stream is still writable.

The standard-stream protocol is CLI control-plane I/O, not a source-declared
model or tool effect. It cannot carry secrets or independently mutate agent
state. The budget admission described below governs the external effect a host
may perform after receiving a grant.

`aster run --fixtures ...`, `aster resume --resolution ...`, and
`aster replay ...` remain available. Replay never opens a host protocol and has
no driver or protocol parameter.

## Protocol envelope

Every ASTER-to-host frame has this envelope:

```json
{
  "schema_version": 1,
  "session_id": "<deterministic run id>",
  "message_id": 0,
  "kind": "hello",
  "payload": {}
}
```

Every host-to-ASTER frame has this envelope:

```json
{
  "schema_version": 1,
  "session_id": "<same session id>",
  "in_reply_to": 0,
  "kind": "hello_ack",
  "payload": {}
}
```

Unknown fields are rejected at every nesting level. ASTER message IDs start at
zero and increase by one. The host only sends replies and must name the exact
outstanding ASTER message. There is never more than one outstanding reply.
Duplicate, stale, skipped, cross-session, or unsolicited frames are failures.

The session ID is the existing deterministic run ID derived from the program
and start-request fingerprints. It is an identity and replay binding, not a
secret.

## Handshake

ASTER emits `hello` before exposing an effect request. Its payload contains:

```json
{
  "protocol": "aster-host",
  "protocol_version": 1,
  "runtime_version": "0.2.0",
  "program_hash": "<sha256>",
  "run_id": "<sha256>"
}
```

The host replies with `hello_ack` containing exactly:

```json
{
  "protocol": "aster-host",
  "protocol_version": 1
}
```

An unsupported protocol, malformed acknowledgement, or EOF fails before any
host effect is admitted.

## Two-phase effect exchange

### 1. Preview

When the VM yields, ASTER appends the `effect_requested` trace entry and emits
`effect_preview`. Its payload contains the complete `EffectRequest` with kind,
identity, typed payload, and request hash. Emitting a preview is not permission
to perform the effect.

The host replies with `effect_admission`:

```json
{
  "request_hash": "<exact request hash>",
  "max_usage": {
    "model_tokens": 2000,
    "money_microunits": 5000
  }
}
```

Only the existing variable dimensions `model_tokens` and
`money_microunits` are legal. Either may be omitted when its maximum is zero.
Fixed call, read, write, and approval counters are reserved internally before
the VM yields and cannot be supplied or altered by the host.

### 2. Admission and durable continuation

ASTER verifies the request hash and reserves every declared maximum atomically.
If any dimension is unknown or exhausted, the session fails without emitting
an execution grant. After successful reservation ASTER:

1. appends `budget_reserved`;
2. checkpoints the trace;
3. seals and atomically writes the pending `MachineSnapshot`;
4. appends `snapshot_written`; and
5. atomically rewrites the trace artifact.

ASTER then creates an `ExecutionGrant`. Its hash is the canonical SHA-256 of
the protocol version, run ID, request hash, trace checkpoint, snapshot hash,
and declared maximum usage. This value is a protocol sequencing token. It does
not replace a source-level capability or `Permit<A>`, and it cannot authorize a
write that ASTER semantics did not already authorize.

ASTER emits `execute_grant` containing the complete request, maximum usage,
snapshot hash, and execution-grant hash. This is the first frame after which a
conforming host may perform the external effect.

### 3. Resolution and settlement

The host replies with `effect_resolution`:

```json
{
  "request_hash": "<exact request hash>",
  "execution_grant_hash": "<exact grant hash>",
  "payload": {},
  "actual_usage": {
    "model_tokens": 714,
    "money_microunits": 1200
  }
}
```

ASTER rejects mismatched request or grant hashes, illegal dimensions, missing
declared dimensions, and actual usage above the admitted maximum. Payload
decoding uses the same declared result type as fixtures and replay. A valid
resolution is appended to the trace, supplied to the VM, and deterministically
settled before execution continues.

When another effect is needed, the preview/admission/grant/resolution exchange
repeats. On successful handler completion ASTER atomically publishes state,
writes the output-state artifact, completes the trace, and emits `completed`
with the final-state hash and trace-chain head. On a controlled failure it
preserves all valid evidence and emits `failed` with a stable diagnostic code
and redacted summary.

## Crash and resume behavior

The durable point is the snapshot written before `execute_grant`. If ASTER
exits before sending the grant, a resumed session re-emits the same grant. If
the host might have executed an effect but lost the resolution, the host must
use the action's idempotency key or provider lookup before replying. ASTER does
not silently retry a write.

`host-resume` verifies the snapshot seal, program hash, trace position, trace
chain head, and pending request. It starts a new protocol transport session
bound to the same deterministic run ID, performs the handshake, and re-emits
the outstanding `execute_grant`. It never asks for a second admission and never
changes the reserved maximum.

After a valid resolution, later crashes use the next effect snapshot. A
completed run cannot be resumed. A snapshot containing an unresolved receipt
still cannot complete until reconciliation succeeds.

## Error model and diagnostics

Host protocol failures use CLI exit class 2 because they are live runtime
boundary failures, not replay divergence or internal panics. The diagnostics
registry gains these meanings without reusing an existing code:

- `ASTER-HOST-11001`: unsupported or malformed protocol frame;
- `ASTER-HOST-11002`: out-of-order, stale, duplicate, or unsolicited reply;
- `ASTER-HOST-11003`: session, request, or execution-grant binding mismatch;
- `ASTER-HOST-11004`: invalid maximum or actual usage declaration;
- `ASTER-HOST-11005`: host EOF before a required reply; and
- `ASTER-HOST-11006`: a protocol frame could not be written completely.

Malformed JSON, invalid UTF-8, oversized lines, and unknown nested fields are
controlled failures. Protocol input is bounded to 1 MiB per line before JSON
decoding. Diagnostics contain hashes, kinds, and identities when safe but never
ordinary private payloads, prompt data, tool results, secrets, or complete
frames.

## Security properties

- The model remains a typed inference oracle and never becomes the host or an
  authority principal inside ASTER.
- Capabilities and fixed budgets are checked before `effect_preview` is
  produced by the already-admitted VM instruction.
- Variable usage is reserved before `execute_grant`.
- Write requests exist only after intent, proposal, policy, and permit checks;
  the host cannot introduce or mutate an action identity or argument.
- The request and grant hashes bind the host response to one admitted effect.
- Secrets are rejected before protocol, trace, snapshot, diagnostics, or
  string conversion.
- Replay accepts no host transport and invokes no driver.
- Standard output cannot mix logs with protocol frames.

The host remains trusted to obey the execution-grant ordering and to report an
authentic provider result and usage. Trace evidence makes violations visible
but cannot sandbox a malicious host. Production adapters should run with only
the operating-system authority corresponding to their declared tools.

## Compatibility and persistence

The host protocol has its own `schema_version` and version negotiation. A
change that alters frame meaning or required fields increments the protocol
version. Unknown versions are rejected; v0.2.0 does not negotiate extensions.

Existing ASTER 0.1 source, fixture files, trace schema, and snapshot schema stay
valid unless implementation reveals an unavoidable persistence change. If a
snapshot field is required for the execution grant, the snapshot schema must
increment and older snapshots must be rejected explicitly rather than guessed
or migrated silently. Trace additions use new entry kinds while retaining the
canonical hash-chain rules. Fixture record/replay behavior remains byte-stable
for an unchanged program and input.

## Example and self-use acceptance

The repository will add a synthetic, temporary-workspace example that exercises
model, read, human approval, write, read-back, and reconciliation through
`aster host`. It must not use credentials, personal data, a live endpoint, or
modify the repository.

Before tagging v0.2.0, Codex will act as the host for this example:

1. receive and answer the model request as a candidate producer;
2. execute the admitted read in the temporary workspace;
3. return an explicit human-approval decision supplied for the test;
4. perform the idempotent admitted write only after `execute_grant`;
5. execute the read-back observation;
6. let ASTER reconcile and publish state; and
7. replay the resulting trace without a host.

The record and replay output states must be byte-identical. The transcript will
record only synthetic values and safe hashes and will be summarized in the
v0.2.0 release notes.

## Test strategy

Runtime unit and integration tests must cover:

- state-machine phase ordering and exact protocol frame serialization;
- all four effect kinds through the two-phase exchange;
- budget exhaustion before any `execute_grant`;
- unknown and duplicate usage dimensions;
- actual usage above the admitted maximum;
- malformed, oversized, unknown-field, wrong-version, stale, duplicate,
  out-of-order, cross-session, request-substitution, and grant-substitution
  frames;
- snapshot creation before the grant and crash/resume of the same admitted
  request;
- no second write admission after uncertain completion;
- record/replay equivalence and zero host interaction during replay;
- trace tamper and semantic divergence rejection;
- secret rejection at protocol, diagnostic, trace, and snapshot boundaries;
- preservation of fixture-driver behavior through the shared
  `RecordSession`; and
- controlled failures with no partial state publication.

CLI black-box tests must drive `aster host` and `aster host-resume` over pipes,
verify that stdout contains only valid protocol frames, verify stderr and exit
classes, and prove that final artifacts are durable and replayable.

The final repository gate remains `./scripts/check.sh` and includes formatter,
clippy, all-feature workspace tests, architecture, documentation, production
panic policy, site contract, and release contract checks.

## Documentation and release

Implementation updates the architecture, runtime/replay and security design
documents, diagnostics registry, CLI reference, README examples, and a
normative ASTER 0.2 host-protocol specification. The ASTER 0.1 language
specification remains the source-language reference and links to the new
runtime protocol specification.

The release work will:

- bump all workspace packages and CLI output to 0.2.0;
- make release archive names and notes derive from the tagged Cargo version
  instead of retaining v0.1.0 literals;
- publish Linux x86_64 musl, macOS arm64, macOS x86_64, and Windows x86_64
  archives plus `SHA256SUMS`;
- update the Operational Amber site and README to v0.2.0;
- merge through green CI, create an annotated immutable `v0.2.0` tag, and let
  the all-or-nothing release workflow publish the assets; and
- externally download every asset, verify checksums and exact archive members,
  smoke-test the Linux binary, verify the self-use trace/replay evidence, and
  confirm the Pages and Release URLs return HTTPS success.

The release remains experimental and unsigned. Checksums prove transport
integrity, not publisher identity, and macOS artifacts are not notarized.
