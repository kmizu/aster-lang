# ASTER v0.1.0 Release and GitHub Pages Design

**Status:** Approved on 2026-08-06

## Objective

Publish the completed ASTER 0.1 reference processor as `v0.1.0`, with
downloadable command-line archives for Linux, macOS, and Windows, a checksum
manifest, curated release notes, and an official GitHub Pages site at
`https://kmizu.github.io/aster-lang/`.

The release must preserve ASTER's actual status: it is an experimental,
fixture-backed reference processor, not a production agent platform and not a
live-provider integration.

## Release source of truth

The current completion branch, `agent/complete-aster-0.1`, contains five
audited completion commits not yet present on `main`. Release work is added to
that branch and reviewed through one pull request into `main`. The merged
`main` commit is the only commit eligible for the `v0.1.0` tag.

Publication is ordered and gated:

1. The release pull request passes CI.
2. The pull request is merged into `main` without rewriting history.
3. CI and the Pages deployment for the merged commit pass.
4. An annotated `v0.1.0` tag is created at that exact `main` commit and pushed.
5. The tag workflow builds and publishes all release archives and
   `SHA256SUMS` together.
6. The public release and Pages site are independently downloaded and checked.

No release is created from an unmerged branch, and no asset is published before
every platform build succeeds.

## Automation boundaries

Three workflows have separate responsibilities and least-privilege tokens.

### Continuous integration

`.github/workflows/ci.yml` continues to run `./scripts/check.sh` for pushes and
pull requests. It installs the pinned Rust 1.96 toolchain and `ripgrep`, because
the production-source policy check explicitly depends on `rg`. The job has
read-only repository contents permission.

### GitHub Pages

`.github/workflows/pages.yml` deploys only the static `site/` directory from
`main` or a manual dispatch. A build job checks the site and uploads the Pages
artifact. A separate deploy job depends on that build and alone receives
`pages: write` and `id-token: write` through the `github-pages` environment.

The workflow uses GitHub's documented Pages actions:

- `actions/configure-pages@v5`
- `actions/upload-pages-artifact@v4`
- `actions/deploy-pages@v4`

### Tagged release

`.github/workflows/release.yml` runs only for tags matching `v*`. It first
checks that the tag is exactly `v` plus the workspace package version. A native
matrix builds four archives:

| Asset | Runner | Rust target | Format |
| --- | --- | --- | --- |
| Linux x86_64 | `ubuntu-24.04` | `x86_64-unknown-linux-musl` | `.tar.gz` |
| macOS Apple Silicon | `macos-15` | `aarch64-apple-darwin` | `.tar.gz` |
| macOS Intel | `macos-15-intel` | `x86_64-apple-darwin` | `.tar.gz` |
| Windows x86_64 | `windows-2025` | `x86_64-pc-windows-msvc` | `.zip` |

Each archive contains only the `aster` executable (`aster.exe` on Windows),
`README.md`, and `LICENSE`. Matrix jobs upload temporary workflow artifacts. A
single Linux publish job downloads all four, verifies the exact asset set,
generates `SHA256SUMS`, and creates the GitHub Release from
`docs/releases/v0.1.0.md`. This job alone receives `contents: write`.

The Linux binary uses musl so the downloadable executable is not tied to the
GitHub runner's glibc version. Release archives are unsigned in 0.1.0; SHA-256
checksums provide transport-integrity verification, not publisher identity.

## Site visual and content design

### Visual thesis

ASTER is presented as a dark operational instrument whose authority transitions
are visible as a warm amber evidence trace. It must look like a governed machine,
not a generic AI SaaS product. Near-black surfaces, ivory text, one amber accent,
thin rules, large condensed-feeling system typography, and monospaced evidence
labels form the complete visual system. The site loads no external fonts,
images, trackers, scripts, or analytics.

### Page structure

The page tells one linear story:

1. **Promise:** ASTER is the brand; “Authority before action.” is the headline.
   Primary action downloads v0.1.0 and secondary action opens the specification.
   An explicit “Experimental reference processor” label prevents production
   readiness from being implied.
2. **Boundary:** a horizontal `Candidate -> Proposal -> Permit ->
   Reconciliation` trace explains the four value transitions and their owners.
3. **Evidence:** a compact meeting-scheduler source excerpt is paired with a
   trace ledger ending in deterministic replay with zero driver calls.
4. **Release:** four direct platform downloads, checksum instructions, version,
   Rust floor, license, and the fixture-only limitation are immediately visible.
5. **Further reading:** links lead to the normative specification,
   architecture, security model, repository, and release notes.

Sections remain cardless. Each section has one job, one dominant visual, and
one takeaway. Desktop uses the full canvas; mobile collapses four-column flows
to two and then one column without horizontal scrolling.

### Motion and accessibility

Three restrained motions establish presence: the hero copy enters once, the
amber authority trace activates stage by stage, and rows reveal on scroll.
Download links use a short underline or background transition on hover and
focus. `prefers-reduced-motion: reduce` disables all nonessential movement.

The page uses semantic landmarks, a skip link, visible keyboard focus,
descriptive link text, WCAG AA color contrast, and no meaning conveyed by color
alone. JavaScript is progressive enhancement: content, navigation, and
downloads remain complete when scripts are unavailable.

## Static site boundaries

The site is deliberately framework-free:

- `site/index.html` owns semantic structure and release copy.
- `site/styles.css` owns the Operational Amber design and responsive behavior.
- `site/site.js` owns only progressive entrance and trace activation.
- `site/404.html` provides a small branded route back to the home page.

No package manager, generated bundle, asset pipeline, or runtime network call is
introduced. Versioned download URLs point directly at the `v0.1.0` GitHub
Release assets so the page is deterministic and does not depend on a “latest”
redirect.

## Documentation and legal surface

The repository adds the canonical Apache License 2.0 text because Cargo already
declares `Apache-2.0` but the repository has no license file. It also adds:

- `docs/releases/v0.1.0.md` for release notes and limitations;
- a README release section with direct Pages, release, checksum, and local build
  links;
- exact CLI archive naming shared by the site and release workflow.

Release notes foreground the implemented safety boundary, deterministic
runtime/replay, meeting-scheduler vertical slice, installation, verification,
and the fixture-only residual risk. They do not claim live network, shell,
provider, package, concurrency, or production key-management support.

## Failure behavior

- Missing `rg`, formatting drift, lint warnings, failing tests, architecture
  drift, or docs drift fail CI before merge.
- A tag/version mismatch fails before any platform build.
- Any missing matrix asset prevents the publish job from creating a release.
- Archive contents outside the executable, README, and license fail the local
  release check.
- A checksum mismatch or a binary that does not report `aster 0.1.0` fails
  external release verification.
- Pages validation rejects external dependencies, missing required anchors,
  missing accessibility hooks, non-versioned download URLs, or absent
  reduced-motion handling.
- Replay and runtime behavior are not changed by the release work.

## Validation

Local and pull-request validation must include:

```bash
./scripts/check-site.sh
./scripts/check-release.sh
./scripts/check.sh
```

After merge, both CI and Pages workflows must be green for the merged `main`
commit. After tagging, every matrix job and the publish job must be green.

External verification downloads all five public assets, runs
`sha256sum --check SHA256SUMS`, confirms the archive member set, runs the Linux
binary with `--version` and `check examples/meeting-scheduler/main.aster`, and
fetches the Pages URL over HTTPS to confirm the release version and direct asset
links. Repository metadata is updated with the Pages homepage URL.

## Non-goals

- Code signing, notarization, Sigstore provenance, Homebrew, crates.io, Winget,
  or installer packages.
- Live provider or tool integrations.
- A documentation generator, search, analytics, custom domain, or CMS.
- A production-readiness claim for ASTER 0.1.
- Changes to ASTER syntax, semantics, IR, runtime, persistence, or security
  boundaries.
