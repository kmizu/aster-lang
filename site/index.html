01 / Why ASTER

Judgment
without authority.

Models are useful where answers require judgment. That is exactly why their output should remain data.

Integration risk
Model response → host tool call

Without an enforced boundary, generated data can be consumed as an instruction beside ambient host authority.

ASTER path
Candidate → validation → governed effect

The runtime keeps data, intent, authority, execution, and observed reality as separate transitions.

02 / Deterministic proof

Prove it in five minutes.

Repository checkout · Bash · Rust 1.96 · synthetic fixtures only.

  1. 01
    Build and check

    Compile the pinned reference processor and validate the program.

    cargo build --release -p aster-cli --bin aster
ASTER_DEMO_DIR=$(mktemp -d)
./target/release/aster check examples/meeting-scheduler/main.aster
  2. 02
    Fixture-backed record

    Execute five synthetic effects and record every governed boundary.

    ./target/release/aster run examples/meeting-scheduler/main.aster \
  --agent Scheduler --event message \
  --input examples/meeting-scheduler/event.json \
  --state examples/meeting-scheduler/initial-state.json \
  --capabilities examples/meeting-scheduler/capabilities.json \
  --fixtures examples/meeting-scheduler/fixtures.json \
  --trace "$ASTER_DEMO_DIR/meeting.trace.jsonl" \
  --snapshot-dir "$ASTER_DEMO_DIR/snapshots" \
  --output-state "$ASTER_DEMO_DIR/record-state.json"
  3. 03
    Driver-free replay

    Re-step the VM without fixtures, a host, or a driver.

    ./target/release/aster replay examples/meeting-scheduler/main.aster \
  --trace "$ASTER_DEMO_DIR/meeting.trace.jsonl" \
  --input examples/meeting-scheduler/event.json \
  --state examples/meeting-scheduler/initial-state.json \
  --capabilities examples/meeting-scheduler/capabilities.json \
  --output-state "$ASTER_DEMO_DIR/replay-state.json"
cmp "$ASTER_DEMO_DIR/record-state.json" \
  "$ASTER_DEMO_DIR/replay-state.json"

03 / Executable evidence

From source to replay,
the boundary stays visible.

The bundled meeting-scheduler program records model, read, human approval, write, reconciliation, transactional state, and replay as deterministic evidence.

meeting-scheduler/main.aster fixture-backed record 
let candidate = (infer ParseMeeting(
  message = msg.value.text,
) using @planner)?;
let request = (validate candidate
  with MeetingRules)?;
let slots = (observe Calendar.free(
  owner = user,
  duration_minutes = request.value.duration_minutes,
))?;
require (len(slots.value) > 0);
let selected = (first(slots.value))?;

let purpose = intent ScheduleMeeting {
  actor = self;
  beneficiary = user;
  basis = [provenance(msg), provenance(request),
           provenance(slots)];
  expected = EventExpectation {
    owner = user, slot_id = selected.id,
  };
  expires_at = add_seconds(event.time, 120);
};

let proposal = propose Calendar.create(
  owner = user, slot = selected,
  title = request.value.title,
  attendees = request.value.attendees,
  request_id = event.id,
) for purpose;
let permit = (authorize proposal
  using CalendarPolicy)?;
let receipt = (commit proposal
  with permit)?;
let actual = (observe Calendar.lookup(
  owner = user, event_id = receipt.value.id,
))?;
let confirmed = (reconcile receipt
  against actual with EventMatches)?;

04 / The authority boundary

The model is an oracle.
Never a principal.

ASTER keeps inference, intent, authority, execution, and observed reality as separate typed transitions. There is no ambient shortcut between them.

01

Candidate<T>

Inference returns opaque data. It cannot be coerced, inspected, persisted, or executed.

Data, not command
02

Proposal<A>

The desired write immutably binds its action, arguments, intent, risk, capability request, and program identity.

Intent, not effect
03

Permit<A>

Authority is expiring, affine, and cryptographically bound to one immutable proposal.

Scoped, then consumed
04

Reconciled<A>

A receipt is not success. A later observation must agree before state can publish.

Evidence, then state

05 / External host boundary

Durable before granted.

A preview is not authority. ASTER reserves budget and persists the continuation before issuing an execute_grant.

  1. 01 effect_preview

    The host may inspect the exact typed request. A preview is not authority.

  2. 02 effect_admission

    ASTER accepts declared maximum usage, reserves budget, and seals the continuation.

  3. 03 execute_grant

    Only the matching grant permits execution after snapshot and trace persistence.

  4. 04 effect_resolution

    ASTER validates the bound typed result, settles usage, and resumes the machine.

The host remains outside ASTER's trust boundary. Process isolation and least privilege remain deployment responsibilities.

07 / Honest scope

A complete vertical slice.
Not a production platform.

Implemented through 0.2

  • Typed candidates, proposals, permits, and reconciliation
  • Capabilities, budgets, pure policies, and human approval
  • Transactional state, hash-chained traces, and snapshots
  • Deterministic record, resume, and driver-free replay
  • Bounded two-phase external-host execution protocol

Deliberately excluded

  • Live model, network, shell, or native provider access
  • Packages, concurrency, loops, recursion, or arbitrary eval
  • Production key management or trace encryption
  • Distributed execution or malicious-host protection
